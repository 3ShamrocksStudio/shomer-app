# SH✡MER iPhone app: parity with the Android app

Branch `ios-native`, 2026-11-03. Every Android entry below is taken from the code, not from older docs.

**How the Android app is built.** It is a Capacitor 6 shell that loads the live web app
(`server.url` = `https://www.shomer-app.co.il/shomer.html`, see `native/capacitor.config.json`).
On top of that sit Capacitor plugins (`native/package.json`) and SH✡MER's own Java layer
(`native/shomer-android/android/app/src/main/java/il/co/shomerapp/*.java`, copied in by
`.github/workflows/android-build.yml`). The iPhone app uses the same structure: the same web
app, the same plugins, and a Swift port of the Java layer (`native/ios/App/App/Shomer*.swift`).
The web layer calls `window.Capacitor.Plugins.ShomerNative` the same way on both platforms.

**Two Android builds.** The website APK (`SHOMER.apk`) keeps every permission. The Google Play
build removes background location, exact alarms, the battery-optimisation request and
high-rate sensors (step "Play build only" in `android-build.yml`). Where the two builds differ,
the table compares iOS with the **website APK**, which has every feature.

Effort: XS < 1 h · S 1–3 h · M 3–8 h · L > 1 day. These are Claude hours on Dave's Mac, plus device testing.
"Done on branch" means the code or config is written. None of it is compiled yet, because that needs Xcode.

## Summary

**Full parity (same plugin or a direct port):** foreground and background location, contacts,
voice answer and spoken fake call, camera selfie and photos, local notifications, notification
permission, phone verification and SMS/phone links, in-app shake, dashboard heartbeat, icon and splash.
Invite links reach parity once the AASA file is on the site.

**Things iOS cannot do, with the best alternative:**

| Android behaviour | Why iOS can't | Best iOS alternative |
|---|---|---|
| Alarm forces max volume | Apps cannot set the system volume | `.playback` session plays through Silent. Critical Alerts entitlement (Apple approval) plays the SOS sound at full volume through mute and DND |
| SOS screen pops over the lock screen | No full-screen intents | Time Sensitive (later Critical) notification, plus the SOS handed to the running web app |
| Always-on background service (shake, polling) | No foreground services; suspended apps can't run code | Kept alive by background location while sharing is on. APNs push for alerts (rows 9–10) |
| Restart after reboot | No boot broadcast | Significant-location-change relaunch (row 6) |
| Power / volume button trigger | Not exposed to apps (Android doesn't use it either) | iPhone's own Emergency SOS, with corrected instructions |
| Torch from the web layer | WKWebView limit | Native `torch` method (row 17) |
